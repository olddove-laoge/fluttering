## cuda编程模型概述
### host
cuda编程可以大致分为两大部分，host函数和kernel函数。Host函数是在CPU侧运行的函数，主要负责 控制和调度：

- 分配/释放内存
- 准备和拷贝数据
- 启动 kernel
- 管理 stream / event / 同步
- 做全局流程控制和业务逻辑
### stream&event
stream被称为CUDA流，是一种抽象机制，它让程序员能够表示一系列按顺序执行的操作。
流的工作方式就像一个任务队列，程序可以把操作（比如内存拷贝、核函数启动）放进队列里，按加入的顺序依次执行。
而图中stream框内kernel之间的event并不是gpu执行的任务(真正的任务是图中的kernel1,2……)，而是某种"标志"，用以标记某任务是否完成，一般用来实现程序的异步或者同步

## cuda执行层级
cuda编程模型中最小的单位为thread，也就是我们熟知的线程。而cuda编程调度的最小单位被称作warp，线程束，一般由32个线程组成。由于是调度的最小单位，同一时间内一个线程束下的线程只能运行同样的程序。32这个数字很特殊，我们后面会见到很多次。
block是有线程组成的线程块，是SM调度的单位(SM是GPU的运算单元)。一般来说，有2D，3D两种block，一个block只能在一个SM上运行，而SM上能有多个block
grid是一次 kernel 启动的所有 blocks，主要作为kernel函数入参使用。
grid还可以分为父网格和子网格，这个我们后面再讲

## cuda内存模型
想了一下，发现还是先将cuda内存模型更合适些，至于执行和其中的细节我们后面再讲
在上图中，很容易发现gpu内存在多级存储结构，包括寄存器(register)、共享内存(shared memory)、全局内存(global memory)与本地内存(local memory)。其实gpu中还存在纹理内存，常量内存之类的……但是好像用的不多？这里只讲前四种
### register
1. 寄存器 (Registers)
- 速度：最快（与 ALU 处于同一流水线）。

- 作用域：内核函数（Kernel）中定义的局部变量（通常是标量，如 int a = 5;）会自动分配到寄存器中。

- 可见性：仅当前 Thread 自己可见。

- 痛点：寄存器资源是极其有限的。如果你的 Kernel 里面写了太多局部变量，或者循环展开过度，就会发生寄存器溢出（Register Spilling）。一旦溢出，数据会被被迫触发到极慢的局部内存（Local Memory）中，程序性能会断崖式下跌。

### Local memory
2. 局部内存 (Local Memory)
- 速度：慢（物理上其实和全局内存是在同一块芯片外 DRAM 上）。

- 作用域：仅当前 Thread 可见。

- 为什么叫“局部”？：它只是名字叫局部，主要是用来存放寄存器装不下的数据（比如比较大的局部数组，或者寄存器溢出后的变量）。

- 痛点：避开它！如果分析工具（如 Nsight Compute）提示你有大量的 Local Memory 访问，说明Kernel 局部变量太多或数组开得太大，需要优化算法。
### Shared Memory
3. 共享内存 (Shared Memory)
- 速度：极快（物理上位于芯片内部的 L1 缓存附近，延迟极低）。

- 作用域：同一个 Block 中的所有 Thread 都可以访问。

- 生命周期：与 Block 相同，Block 执行结束，数据释放。

- 核心用途：它是线程间通信（合作）的桥梁。通常的用法是：把全局内存（Global Memory）中需要频繁复用的数据，批量“拉”到 Shared Memory 中，然后让 Block 内的线程并发访问。

- 痛点：

    - 容量小：通常每个 Block 只有几十 KB（比如 48KB 或 96KB）。

    - 银行冲突 (Bank Conflict)：Shared Memory 被分为 32 个等宽的 Bank。如果一个 Warp（32个线程）中的多个线程同时访问同一个 Bank 的不同地址，就会发生冲突，导致访问串行化。

关于银行冲突的问题，我觉得完全可以单独开一章讲
### bank冲突
共享内存有个特殊的形式是，分为32个同样大小的内存模型，称为存储体，可以同时访问。32个存储体的目的是对应一个线程束中有32个线程，这些线程在访问共享内存的时候，如果都访问不同存储体（无冲突），那么一个事务就能够完成，否则（有冲突）需要多个内存事务了，这样带宽利用率降低。
在cuda编程中，我们会经常用到并行访存和计算，会导致多个线程同时访问shared memory，此时就很容易发生访问冲突导致效率下降的问题
如果访问的是同一个bank的同一段地址还好，这时候，一个内存事务执行完毕后，一个线程得到了这个地址的数据，他会通过广播的形式告诉其他所有线程，可以一定程度上避免冲突的发生，倘若是不同地址，冲突就会十分严重
![image](/images/posts/1779772888743-yw00y7.png)

### bank冲突解决方式
官方的方法是给线程数组加一列
官方给出的例子是二维矩阵转置
在二维矩阵的转置中，矩阵的大小通常为32*32
`__shared__ float smemArray[32][32]; // 未优化的定义`
在物理上，这个二维数组在内存中是连续一维线性排列的。因为每行有 32 个元素，刚好等于 Bank 的数量（32）。这意味着：
第一行 smemArray[0][0] 到 smemArray[0][31] 完美地占满了 Bank 0 到 Bank 31。
第二行 smemArray[1][0] 的地址是 0 + 32 = 32。根据 32 取模规则，它又掉进了 Bank 0！
依此类推，每一列的所有元素，物理上都挤在同一个 Bank 里。
当进行矩阵转置时，线程通常需要按列读取共享内存（例如 smemArray[threadIdx.y][threadIdx.x]）。
此时，同一个 Warp 里的 32 个线程会同时去读取同一列的不同行。因为整列都在同一个 Bank 里，32 个请求被迫串行化，这就引发了严重的 32路 Bank 冲突。

为了解决bank冲突的问题，官方给出的方案是给二维数组的主维（列数）额外多塞一个空位置：
当我们把列数变成 33 之后，内存的线性映射发生了错位（错开了一个位置）：

第 0 行：占满 Bank 0 到 Bank 31，还剩下一个尾巴 smemArray[0][32] 掉在了下一轮的 Bank 0。

第 1 行：它的起点 smemArray[1][0] 顺延到了 Bank 1。

第 2 行：它的起点 smemArray[2][0] 顺延到了 Bank 2。

这就形成了一个斜线错位的效果。我们再来看此时如果 Warp 按列读取第一列（[0][0], [1][0], [2][0]...）：

smemArray[0][0] 处于 Bank 0

smemArray[1][0] 处于 Bank 1

smemArray[2][0] 处于 Bank 2

...

原本挤在同一个 Bank 的一列元素，被这个多出来的“虚空列”完美错开到了 32 个不同的 Bank 中。当 Warp 里的 32 个线程再次同时按列读取时，每个人对应的都是不同的 Bank，冲突瞬间降为 0。

### Gloabl Memory
全局内存也有很多可以谈的点，也是和访问冲突，下面我来慢慢讲一下
核函数运行时需要从全局内存（DRAM）中读取数据，有两种粒度，分别为128字节和32字节
我们先以128字节为例讲解，也就是使用一级缓存时
全局内存访问的问题主要在对齐方面，一个期望的访存应该是类似下图的
![image](/images/posts/1779780966846-7u7b91.png)
可以看到，32个线程访问的128个字节完美和一个数据段对齐，此时利用率为128/128*100% = 100%
但如果访问的字节比较散乱，就会导致利用率下降，比如说下图
![image](/images/posts/1779781181851-2psk5k.png)
数据分散开了，thread0的请求在128之前，后面还有请求在256之后，所以需要三个内存事务，而利用率，也就是从主存取回来的数据被使用到的比例，只有 1281/28×3
的比例。这个比例低会造成带宽的浪费，最极端的表现，就是如果每个线程的请求都在不同的段，也就是一个128字节的事务只有1个字节是有用的，那么利用率只有 1/128

当不使用一级缓存的时候，内存事务的粒度变为32字节，更细粒度的好处是提高利用律，这个很好理解，比如你每次喝水只能选择一瓶大瓶500ml的或则一个小瓶的250ml，当你非常渴的时候需要400ml水分，喝大瓶的，比较方便，因为如果喝小瓶的一瓶不够，还需要再喝一瓶，此时大瓶的方便.但如果你需要200ml的水分的时候，小瓶的利用率就高很多。细粒度的访问就是用小瓶喝水，虽然体积小，但是每次的利用率都高了不少，针对上面使用缓存的情况5，可能效果会更好。
